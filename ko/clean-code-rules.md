# AI 코드 생성을 위한 클린 코드 규칙

이 규칙은 유지보수하기 쉽고 전문가 수준의 코드를 만들도록 코드 생성을 안내합니다.

## 의미 있는 이름
- 무엇이 왜 있는지 드러내는 이름을 씁니다
- 잘못된 정보를 주거나 의미 없이 구분하는 이름(예: `data`, `info`, `manager`)을 피합니다
- 발음할 수 있고 검색할 수 있는 이름을 씁니다
- 클래스 이름: 명사 (예: `UserAccount`, `PaymentProcessor`)
- 메서드 이름: 동사 (예: `calculateTotal`, `sendEmail`)
- 머릿속으로 변환해야 하는 이름과 인코딩(헝가리안 표기법, 접두사)을 피합니다

## 함수
- 함수는 작게 유지합니다 (20줄 미만이 이상적)
- 한 가지 일만 합니다 - 단일 책임 원칙(Single Responsibility Principle)
- 함수 하나에는 추상화 수준을 하나만 둡니다
- 인수를 제한합니다: 0~2개가 이상적이고 최대 3개, 플래그 인수는 피합니다
- 부수 효과를 두지 않습니다 - 함수는 이름이 말하는 일만 해야 합니다
- 명령(상태 변경)과 조회(정보 반환)를 분리합니다
- 오류 코드보다 예외를 씁니다

## 주석
- 코드는 스스로 설명해야 합니다 - 되도록 주석을 피합니다
- 좋은 주석: 법적 정보, 경고, TODO, 공개 API 문서
- 나쁜 주석: 중복된 주석, 오해를 부르는 주석, 나쁜 코드를 변명하는 주석
- 코드를 주석 처리하지 말고 지웁니다 (버전 관리가 기록을 보존합니다)
- 주석이 필요하다면 먼저 코드를 리팩터링할 수 없는지 생각합니다

## 형식 맞추기
- 파일은 작고 한 가지에 집중하게 유지합니다
- 세로 형식: 관련 개념은 가까이 두고, 빈 줄로 개념을 나눕니다
- 가로 형식: 줄 길이를 제한합니다 (80~120자)
- 일관된 들여쓰기와 팀 스타일을 씁니다
- 관련 함수는 함께 묶습니다

## 객체와 자료 구조
- 객체: 데이터는 추상화 뒤에 숨기고, 동작은 메서드로 드러냅니다
- 자료 구조: 데이터를 드러내고, 동작은 최소한으로 둡니다
- 디미터 법칙(Law of Demeter): 가까운 객체하고만 이야기하고, `a.getB().getC().doSomething()` 같은 호출은 피합니다
- getter/setter로 내부 구조를 무작정 드러내지 않습니다

## 오류 처리
- 반환 코드나 오류 플래그 대신 예외를 씁니다
- 실패할 수 있는 코드라면 `try-catch-finally`부터 씁니다
- 예외 메시지에 맥락을 담습니다
- `null`을 반환하지 말고 빈 컬렉션을 반환하거나 Optional/Maybe를 씁니다
- 인수로 `null`을 넘기지 않습니다

## 클래스
- 작은 클래스: 크기는 줄 수가 아니라 책임으로 잽니다
- 단일 책임 원칙: 변경할 이유가 하나뿐이어야 합니다
- 높은 응집도: 클래스 변수를 여러 메서드가 씁니다
- 낮은 결합도: 클래스 사이 의존성을 최소로 합니다
- 개방/폐쇄 원칙(Open/Closed Principle): 확장에는 열려 있고 수정에는 닫혀 있습니다

## 단위 테스트
- 빠르고(Fast), 독립적이고(Independent), 반복 가능하고(Repeatable), 스스로 검증하고(Self-validating), 적시에(Timely) 작성합니다 (F.I.R.S.T.)
- 테스트 하나에 assert 하나 (또는 개념 하나)
- 테스트 코드도 운영 코드와 같은 품질로 씁니다
- 무엇을 테스트하는지 설명하는 읽기 쉬운 테스트 이름을 씁니다
- Arrange-Act-Assert(준비-실행-검증) 패턴

## 코드 품질 원칙
- **DRY (Don't Repeat Yourself)**: 중복을 두지 않습니다
- **YAGNI (You Aren't Gonna Need It)**: 가정에 불과한 미래를 위해 만들지 않습니다
- **KISS (Keep It Simple)**: 불필요한 복잡성을 피합니다
- **보이스카우트 규칙(Boy Scout Rule)**: 코드를 처음 봤을 때보다 깨끗하게 남깁니다

## 피해야 할 코드 스멜
- 긴 함수나 클래스
- 중복 코드
- 죽은 코드 (쓰지 않는 변수, 함수, 매개변수)
- Feature envy(기능 욕심) (다른 클래스에 더 관심이 많은 메서드)
- Inappropriate intimacy(부적절한 친밀) (서로에 대해 너무 많이 아는 클래스)
- 긴 매개변수 목록
- Primitive obsession(기본형 집착) (작은 객체 대신 기본형을 남용)
- switch/case 문 (다형성을 고려)
- Temporary field(임시 필드) (가끔만 쓰이는 클래스 변수)

## 동시성
- 동시성 코드는 다른 코드와 분리합니다
- 동기화되거나 잠기는 데이터의 범위를 제한합니다
- 스레드 안전한 컬렉션을 씁니다
- 동기화 구간은 작게 유지합니다
- 실행 모델과 기본 요소를 이해합니다

## 시스템 설계
- 생성과 사용을 분리합니다 (의존성 주입)
- 복잡한 객체 생성에는 팩토리나 빌더를 씁니다
- 구현이 아니라 인터페이스에 맞춰 프로그래밍합니다
- 상속보다 합성을 선호합니다
- 디자인 패턴은 자랑하려고가 아니라 단순해질 때 적용합니다

## 리팩터링
- 한꺼번에 몰아서 하지 말고 꾸준히 리팩터링합니다
- 전후에 항상 테스트가 통과해야 합니다
- 작은 단계: 한 번에 한 가지만 바꿉니다
- 자주 쓰는 리팩터링: Extract Method(메서드 추출), Rename(이름 바꾸기), Move(옮기기), Inline(인라인)

## 문서화
- 스스로 설명하는 코드 > 주석 > 외부 문서
- 공개 API에는 명확한 문서가 필요합니다
- 문서에 예제를 넣습니다
- 문서는 코드 가까이(되도록 코드 안에) 둡니다
