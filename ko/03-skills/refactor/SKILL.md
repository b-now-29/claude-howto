# 코드 리팩터링 스킬

Martin Fowler의 *Refactoring: Improving the Design of Existing Code* (2판)에 기반한 체계적인 리팩터링 방법입니다. 테스트로 뒷받침되는 안전하고 점진적인 변경을 강조합니다.

> "리팩터링은 코드의 외부 동작은 바꾸지 않으면서 내부 구조를 개선하는 방식으로 소프트웨어 시스템을 바꾸는 과정이다." — Martin Fowler

## 핵심 원칙

1. **동작 보존**: 외부 동작은 바뀌지 않아야 합니다
2. **작은 단계**: 작고 테스트할 수 있는 변경을 합니다
3. **테스트 주도**: 테스트가 안전망입니다
4. **지속적으로**: 리팩터링은 한 번으로 끝나는 일이 아니라 계속하는 일입니다
5. **협업**: 단계마다 사용자 승인이 필요합니다

## 워크플로 개요

```text
1단계: 조사와 분석
    ↓
2단계: 테스트 커버리지 평가
    ↓
3단계: 코드 스멜 찾기
    ↓
4단계: 리팩터링 계획 세우기
    ↓
5단계: 점진적 구현
    ↓
6단계: 검토와 반복
```

---

## 1단계: 조사와 분석

### 목표
- 코드베이스의 구조와 목적을 이해합니다
- 리팩터링 범위를 정합니다
- 비즈니스 요구 사항에 대한 맥락을 모읍니다

### 사용자에게 물을 질문
시작하기 전에 다음을 확인합니다.

1. **범위**: 어떤 파일/모듈/함수를 리팩터링해야 하나요?
2. **목표**: 어떤 문제를 해결하려고 하나요? (가독성, 성능, 유지 보수성)
3. **제약**: 바꾸면 **안 되는** 부분이 있나요?
4. **일정 압박**: 이 작업이 다른 작업을 막고 있나요?
5. **테스트 상태**: 테스트가 있나요? 통과하고 있나요?

### 할 일
- [ ] 대상 코드를 읽고 이해하기
- [ ] 의존성과 연동 지점 파악하기
- [ ] 현재 아키텍처 문서화하기
- [ ] 기존 기술 부채 표시(TODO, FIXME) 기록하기

### 결과물
사용자에게 다음을 보여 줍니다.
- 코드 구조 요약
- 찾은 문제 영역
- 초기 권고
- **진행 승인 요청**

---

## 2단계: 테스트 커버리지 평가

### 테스트가 중요한 이유
> "테스트 없이 리팩터링하는 것은 안전벨트 없이 운전하는 것과 같다." — Martin Fowler

테스트는 안전한 리팩터링을 가능하게 하는 **핵심 수단**입니다. 테스트가 없으면 버그를 만들 위험이 있습니다.

### 평가 단계

1. **기존 테스트 확인**
   ```bash
   # 테스트 파일 찾기
   find . -name "*test*" -o -name "*spec*" | head -20
   ```

2. **기존 테스트 실행**
   ```bash
   # JavaScript/TypeScript
   npm test

   # Python
   pytest -v

   # Java
   mvn test
   ```

3. **커버리지 확인 (가능한 경우)**
   ```bash
   # JavaScript
   npm run test:coverage

   # Python
   pytest --cov=.
   ```

### 결정 지점: 사용자에게 묻기

**테스트가 있고 통과하면:**
- 3단계로 진행합니다

**테스트가 없거나 부족하면:**
다음 선택지를 보여 줍니다.
1. 테스트를 먼저 작성 (권장)
2. 리팩터링하면서 테스트를 조금씩 추가
3. 테스트 없이 진행 (위험함 - 사용자의 확인이 필요)

**테스트가 실패하면:**
- 멈춥니다. 리팩터링 전에 실패하는 테스트를 고칩니다
- 사용자에게 묻습니다: 테스트부터 고칠까요?

### 테스트 작성 가이드라인 (필요한 경우)

리팩터링하는 함수마다 테스트가 다음을 다루는지 확인합니다.
- 정상 경로 (일반적인 동작)
- 경계 사례 (빈 입력, null, 경곗값)
- 오류 시나리오 (잘못된 입력, 예외)

"레드-그린-리팩터" 주기를 씁니다.
1. 실패하는 테스트 작성 (레드)
2. 통과하게 만들기 (그린)
3. 리팩터링

## 3단계: 코드 스멜 찾기

### 코드 스멜이란?
코드에 숨은 더 깊은 문제의 증상입니다. 버그는 아니지만, 코드를 개선할 여지가 있다는 신호입니다.

### 확인할 흔한 코드 스멜

전체 목록은 [references/code-smells.md](references/code-smells.md)를 참고하세요.

#### 빠른 참고

| 스멜 | 징후 | 영향 |
|------|------|------|
| **Long Method** (긴 메서드) | 30~50줄을 넘는 메서드 | 이해, 테스트, 유지 보수가 어려움 |
| **Duplicated Code** (중복 코드) | 같은 로직이 여러 곳에 있음 | 버그를 여러 곳에서 고쳐야 함 |
| **Large Class** (거대한 클래스) | 책임이 너무 많은 클래스 | 단일 책임 원칙 위반 |
| **Feature Envy** (기능 편애) | 메서드가 다른 클래스의 데이터를 더 많이 씀 | 캡슐화가 약함 |
| **Primitive Obsession** (기본형 집착) | 객체 대신 기본형을 지나치게 씀 | 도메인 개념이 빠짐 |
| **Long Parameter List** (긴 매개변수 목록) | 매개변수가 4개 이상인 메서드 | 올바르게 호출하기 어려움 |
| **Data Clumps** (데이터 뭉치) | 같은 데이터 항목이 늘 함께 나타남 | 추상화가 빠짐 |
| **Switch Statements** (switch 문) | 복잡한 switch/if-else 사슬 | 확장하기 어려움 |
| **Speculative Generality** (추측성 일반화) | "혹시 몰라서" 만든 코드 | 불필요한 복잡도 |
| **Dead Code** (죽은 코드) | 쓰이지 않는 코드 | 혼란, 유지 보수 부담 |

### 분석 단계

1. **자동 분석** (스크립트가 있는 경우)
   ```bash
   python scripts/detect-smells.py <file>
   ```

2. **직접 검토**
   - 코드를 체계적으로 훑어봅니다
   - 스멜마다 위치와 심각도를 기록합니다
   - 영향에 따라 분류합니다 (Critical/High/Medium/Low)

3. **우선순위 정하기**
   다음 같은 스멜에 집중합니다.
   - 현재 개발을 막는 것
   - 버그나 혼란을 일으키는 것
   - 가장 자주 바뀌는 코드 경로에 영향을 주는 것

### 결과물: 스멜 보고서

사용자에게 다음을 보여 줍니다.
- 위치가 포함된 스멜 목록
- 각 스멜의 심각도 평가
- 권장 우선순위
- **우선순위 승인 요청**

## 4단계: 리팩터링 계획 세우기

### 리팩터링 고르기

스멜마다 카탈로그에서 알맞은 리팩터링을 고릅니다.

전체 목록은 [references/refactoring-catalog.md](references/refactoring-catalog.md)를 참고하세요.

#### 스멜과 리팩터링 대응표

| 코드 스멜 | 권장 리팩터링 |
|-----------|---------------|
| Long Method | Extract Method, Replace Temp with Query |
| Duplicated Code | Extract Method, Pull Up Method, Form Template Method |
| Large Class | Extract Class, Extract Subclass |
| Feature Envy | Move Method, Move Field |
| Primitive Obsession | Replace Primitive with Object, Replace Type Code with Class |
| Long Parameter List | Introduce Parameter Object, Preserve Whole Object |
| Data Clumps | Extract Class, Introduce Parameter Object |
| Switch Statements | Replace Conditional with Polymorphism |
| Speculative Generality | Collapse Hierarchy, Inline Class, Remove Dead Code |
| Dead Code | Remove Dead Code |

### 계획 구조

[templates/refactoring-plan.md](templates/refactoring-plan.md)의 템플릿을 씁니다.

리팩터링마다:
1. **대상**: 어떤 코드가 바뀌는지
2. **스멜**: 어떤 문제를 다루는지
3. **리팩터링**: 어떤 기법을 적용하는지
4. **단계**: 자세한 작은 단계
5. **위험**: 무엇이 잘못될 수 있는지
6. **되돌리기**: 필요하면 어떻게 되돌리는지

### 단계별 접근

**중요**: 리팩터링은 단계를 나눠 점진적으로 도입합니다.

**A단계: 빠른 성과** (위험 낮음, 가치 높음)
- 명확하게 알 수 있도록 변수 이름 바꾸기
- 뻔한 중복 코드 추출하기
- 죽은 코드 지우기

**B단계: 구조 개선** (위험 중간)
- 긴 함수에서 메서드 추출하기
- 매개변수 객체 도입하기
- 메서드를 알맞은 클래스로 옮기기

**C단계: 아키텍처 변경** (위험 높음)
- 조건문을 다형성으로 바꾸기
- 클래스 추출하기
- 디자인 패턴 도입하기

### 결정 지점: 사용자에게 계획 보여 주기

구현하기 전에:
- 전체 리팩터링 계획을 보여 줍니다
- 각 단계와 그 위험을 설명합니다
- 단계마다 명시적인 승인을 받습니다
- **묻기**: "A단계를 진행할까요?"

## 5단계: 점진적 구현

### 황금률
> "변경 → 테스트 → 통과? → 커밋 → 다음 단계"

### 구현 리듬

리팩터링 단계마다:

1. **사전 확인**
   - 테스트가 통과함 (그린)
   - 코드가 컴파일됨

2. **작은 변경 **하나**만 하기**
   - 카탈로그의 절차를 따릅니다
   - 변경을 최소한으로 유지합니다

3. **확인**
   - 바로 테스트를 실행합니다
   - 컴파일 오류를 확인합니다

4. **테스트가 통과하면 (그린)**
   - 내용을 알 수 있는 메시지로 커밋합니다
   - 다음 단계로 넘어갑니다

5. **테스트가 실패하면 (레드)**
   - 바로 멈춥니다
   - 변경을 되돌립니다
   - 무엇이 잘못되었는지 분석합니다
   - 불분명하면 사용자에게 묻습니다

### 커밋 전략

각 커밋은 다음과 같아야 합니다.
- **원자적**: 논리적 변경 하나
- **되돌릴 수 있음**: 쉽게 되돌릴 수 있음
- **설명적**: 명확한 커밋 메시지

커밋 메시지 예시:
```text
refactor: Extract calculateTotal() from processOrder()
refactor: Rename 'x' to 'customerCount' for clarity
refactor: Remove unused validateOldFormat() method
```

### 진행 상황 보고

하위 단계를 마칠 때마다 사용자에게 보고합니다.
- 한 변경
- 테스트가 여전히 통과하는지
- 겪은 문제
- **묻기**: "다음 묶음을 계속할까요?"

## 6단계: 검토와 반복

### 리팩터링 후 체크리스트

- [ ] 모든 테스트가 통과함
- [ ] 새 경고/오류가 없음
- [ ] 코드가 컴파일됨
- [ ] 동작이 바뀌지 않음 (직접 확인)
- [ ] 필요하면 문서를 업데이트함
- [ ] 커밋 기록이 깔끔함

### 지표 비교

변경 전과 후에 복잡도 분석을 실행합니다.
```bash
python scripts/analyze-complexity.py <file>
```

개선 결과를 보여 줍니다.
- 코드 줄 수 변화
- 순환 복잡도 변화
- 유지 보수성 지수 변화

### 사용자 검토

최종 결과를 보여 줍니다.
- 모든 변경 요약
- 변경 전/후 코드 비교
- 지표 개선
- 남은 기술 부채
- **묻기**: "이 변경 사항에 만족하시나요?"

### 다음 단계

사용자와 논의합니다.
- 더 다룰 스멜이 있는지
- 후속 리팩터링 일정을 잡을지
- 다른 곳에도 비슷한 변경을 적용할지

## 중요한 가이드라인

### 멈추고 물어야 할 때

다음 경우에는 항상 멈추고 사용자와 상의합니다.
- 비즈니스 로직이 확실하지 않을 때
- 변경이 외부 API에 영향을 줄 수 있을 때
- 테스트 커버리지가 부족할 때
- 중요한 아키텍처 결정이 필요할 때
- 위험 수준이 올라갈 때
- 예상치 못한 복잡도를 만났을 때

### 안전 규칙

1. **테스트 없이 리팩터링하지 않기** (사용자가 위험을 명시적으로 받아들인 경우는 예외)
2. **큰 변경을 하지 않기** - 작은 단계로 나누기
3. **변경할 때마다 테스트 실행을 건너뛰지 않기**
4. **테스트가 실패하면 계속하지 않기** - 먼저 고치거나 되돌리기
5. **가정하지 않기** - 애매하면 묻기

### 하지 말아야 할 것

- 리팩터링과 기능 추가를 섞지 않습니다
- 운영 장애 대응 중에 리팩터링하지 않습니다
- 이해하지 못한 코드를 리팩터링하지 않습니다
- 과도하게 설계하지 않습니다 - 단순하게 유지합니다
- 모든 것을 한 번에 리팩터링하지 않습니다

## 빠른 시작 예시

### 상황: 중복이 있는 긴 메서드

**이전:**
```javascript
function processOrder(order) {
  // 다음을 포함한 150줄의 코드:
  // - 중복된 검증 로직
  // - 인라인 계산
  // - 뒤섞인 책임
}
```

**리팩터링 단계:**

1. processOrder()에 **테스트가 있는지 확인**합니다
2. 검증 로직을 validateOrder()로 **추출**합니다
3. **테스트** - 통과해야 합니다
4. 계산을 calculateOrderTotal()로 **추출**합니다
5. **테스트** - 통과해야 합니다
6. 알림을 notifyCustomer()로 **추출**합니다
7. **테스트** - 통과해야 합니다
8. **검토** - 이제 processOrder()는 명확한 함수 3개를 조율합니다

**이후:**
```javascript
function processOrder(order) {
  validateOrder(order);
  const total = calculateOrderTotal(order);
  notifyCustomer(order, total);
  return { order, total };
}
```
