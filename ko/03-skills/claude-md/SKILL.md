## 사용자 입력

```text
$ARGUMENTS
```

진행하기 전에 사용자 입력이 비어 있지 않다면 **반드시** 고려해야 합니다. 사용자는 다음을 지정할 수 있습니다.
- `create` - 새 CLAUDE.md를 처음부터 만들기
- `update` - 기존 CLAUDE.md 개선하기
- `audit` - 현재 CLAUDE.md의 품질을 분석하고 보고하기
- 만들거나 업데이트할 특정 경로 (예: 디렉터리별 지침용 `src/api/CLAUDE.md`)

## 핵심 원칙

**LLM은 상태가 없습니다**: CLAUDE.md는 모든 대화에 (자동 메모리, 범위가 정해지지 않은 규칙과 함께) 불러오는 주 프로젝트 파일입니다. AI 에이전트가 코드베이스에 적응하도록 돕는 가장 중요한 온보딩 문서 역할을 합니다.

### 황금률

1. **적을수록 좋다**: 최신 LLM은 약 150~200개의 지침을 따를 수 있습니다. Claude Code의 시스템 프롬프트가 이미 약 50개를 씁니다. CLAUDE.md는 핵심에 집중하고 간결하게 유지하세요.

2. **어디에나 적용될 것**: 모든 세션에 관련된 정보만 넣습니다. 특정 작업용 지침은 별도 파일에 둡니다.

3. **Claude를 린터로 쓰지 말 것**: 스타일 가이드라인은 컨텍스트를 부풀리고 지침을 따르는 능력을 떨어뜨립니다. 대신 결정론적 도구(prettier, eslint 등)를 쓰세요.

4. **자동 생성하지 말 것**: CLAUDE.md는 AI 실행 환경에서 가장 효과가 큰 지점입니다. 신중하게 생각하며 직접 작성하세요.

## 실행 흐름

### 1. 프로젝트 분석

먼저 현재 프로젝트 상태를 분석합니다.

1. 기존 CLAUDE.md 파일을 확인합니다:
   - 루트 단위: `./CLAUDE.md` 또는 `.claude/CLAUDE.md`
   - 디렉터리별: `**/CLAUDE.md`
   - 전역 사용자 설정: `~/.claude/CLAUDE.md`

2. 프로젝트 구조를 파악합니다:
   - 기술 스택 (언어, 프레임워크)
   - 프로젝트 유형 (모노레포, 단일 앱, 라이브러리)
   - 개발 도구 (패키지 관리자, 빌드 시스템, 테스트 실행기)

3. 기존 문서를 검토합니다:
   - README.md
   - CONTRIBUTING.md
   - package.json, pyproject.toml, Cargo.toml 등

### 2. 내용 전략 (무엇, 왜, 어떻게)

CLAUDE.md는 세 가지 축으로 구성합니다.

#### 무엇 - 기술과 구조
- 기술 스택 개요
- 프로젝트 구성 (모노레포에서 특히 중요)
- 핵심 디렉터리와 그 용도

#### 왜 - 목적과 맥락
- 프로젝트가 하는 일
- 특정 아키텍처 결정을 내린 이유
- 각 주요 구성 요소가 맡은 일

#### 어떻게 - 워크플로와 규칙
- 개발 워크플로 (bun 또는 node, pip 또는 uv 등)
- 테스트 절차와 명령
- 검증과 빌드 방법
- 중요한 "함정"이나 한눈에 알기 어려운 요구 사항

### 3. 점진적 공개 전략

큰 프로젝트라면 `agent_docs/` 폴더를 만들도록 권합니다.

```text
agent_docs/
  |- building_the_project.md
  |- running_tests.md
  |- code_conventions.md
  |- architecture_decisions.md
```

CLAUDE.md에서는 다음과 같은 지침으로 이 파일들을 참조합니다.
```markdown
자세한 빌드 방법은 `agent_docs/building_the_project.md`를 참고하세요
```

**중요**: 오래된 컨텍스트를 피하려면 코드 조각 대신 `file:line` 참조를 쓰세요.

### 4. 품질 제약

CLAUDE.md를 만들거나 업데이트할 때:

1. **목표 길이**: 200줄 이하로 유지합니다. 짧을수록 좋습니다
2. **스타일 규칙 금지**: 린트/포맷 지침은 모두 뺍니다
3. **특정 작업용 지침 금지**: 별도 파일로 옮깁니다
4. **코드 조각 금지**: 대신 파일 참조를 씁니다
5. **중복 정보 금지**: package.json이나 README에 있는 내용을 반복하지 않습니다

### 5. 꼭 필요한 단락

잘 구성된 CLAUDE.md에는 다음이 들어 있어야 합니다.

```markdown
# 프로젝트 이름

한 줄짜리 짧은 설명.

## 기술 스택
- 주 언어와 버전
- 핵심 프레임워크/라이브러리
- 데이터베이스/저장소 (있는 경우)

## 프로젝트 구조
[모노레포나 복잡한 구조일 때만]
- `apps/` - 애플리케이션 진입점
- `packages/` - 공유 라이브러리

## 개발 명령
- 설치: `command`
- 테스트: `command`
- 빌드: `command`

## 중요한 규칙
[한눈에 알기 어렵고 영향이 큰 규칙만]
- 짧은 설명이 붙은 규칙 1
- 짧은 설명이 붙은 규칙 2

## 알려진 문제 / 함정
[개발자가 계속 걸려 넘어지는 것]
- 문제 1
- 문제 2
```

### 6. 피해야 할 안티 패턴

**넣지 말아야 할 것:**
- 코드 스타일 가이드라인 (린터를 쓰세요)
- Claude 사용법에 대한 문서
- 뻔한 패턴에 대한 긴 설명
- 복사해 붙인 코드 예시
- 일반적인 모범 사례 ("깔끔한 코드 쓰기")
- 특정 작업용 지침
- 자동 생성된 내용
- 긴 TODO 목록

### 7. 검증 체크리스트

마무리하기 전에 확인합니다.

- [ ] 200줄 이하로 유지했다. 짧을수록 좋다
- [ ] 모든 줄이 모든 세션에 적용된다
- [ ] 스타일/포맷 규칙이 없다
- [ ] 코드 조각이 없다 (파일 참조를 씀)
- [ ] 명령이 실제로 작동하는지 확인했다
- [ ] 복잡한 프로젝트에는 점진적 공개를 썼다
- [ ] 중요한 함정을 문서화했다
- [ ] README.md와 중복되지 않는다

## 출력 형식

### `create` 또는 기본값일 때:

1. 프로젝트를 분석합니다
2. 위 구조에 따라 CLAUDE.md 초안을 씁니다
3. 검토를 위해 초안을 보여 줍니다
4. 승인을 받은 뒤 알맞은 위치에 씁니다

### `update`일 때:

1. 기존 CLAUDE.md를 읽습니다
2. 모범 사례와 비교해 감사합니다
3. 다음을 찾습니다:
   - 뺄 내용 (스타일 규칙, 코드 조각, 특정 작업용 내용)
   - 줄일 내용
   - 빠진 핵심 정보
4. 검토를 위해 변경 사항을 보여 줍니다
5. 승인을 받은 뒤 변경 사항을 적용합니다

### `audit`일 때:

1. 기존 CLAUDE.md를 읽습니다
2. 다음 내용이 담긴 보고서를 만듭니다:
   - 현재 줄 수와 목표 비교
   - 모든 세션에 적용되는 내용의 비율
   - 찾은 안티 패턴 목록
   - 개선 권고
3. 파일은 수정하지 말고 보고만 합니다

## AGENTS.md 다루기

사용자가 AGENTS.md를 만들거나 업데이트해 달라고 하면:

**v2.1.277부터 Claude Code는 `AGENTS.md`를 프로젝트 지침으로 바로 읽습니다.** 다만 작업 디렉터리와 그 위의 모든 디렉터리에 `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md`가 없을 때만입니다. `~/.claude/CLAUDE.md`, 관리형 CLAUDE.md, `.claude/rules/`는 이 검사에 포함되지 않으며 함께 계속 불러옵니다. 어떤 파일을 읽을지는 `/config`의 **Project instructions**로 정합니다: `claude-md-or-agents-md` (기본값), `claude-md-and-agents-md`, `claude-md`, `managed-only`. 바로 읽을 수 없는 경우(v2.1.277 이전 버전, Bedrock/Vertex/Foundry, LLM 게이트웨이, 텔레메트리를 끈 경우에는 v2.1.281 이전, 또는 업그레이드 후 첫 세션)에는 CLAUDE.md에서 `@AGENTS.md`로 가져오거나 `CLAUDE.md`를 그 파일로 심볼릭 링크하는 방식으로 대신합니다.

AGENTS.md는 여러 도구가 함께 쓰는 프로젝트 컨텍스트 파일입니다. 에이전트 정의 형식이 아니라 CLAUDE.md와 같은 *종류*의 문서입니다. 여러 코딩 에이전트가 하나의 프로젝트 규칙을 공유하려고 쓰며, 다음을 담습니다.
- 빌드, 테스트, 린트 명령
- 코드 스타일과 아키텍처 규칙
- 저장소 구성과 각 파일의 위치

서브에이전트는 AGENTS.md가 아니라 `.claude/agents/*.md`에 따로 정의합니다.

비슷한 원칙을 적용합니다:
- 핵심에 집중하고 간결하게 유지합니다
- 점진적 공개를 씁니다
- 내용을 넣는 대신 외부 문서를 참조합니다

## 메모

- 명령을 넣기 전에 항상 작동하는지 확인합니다
- 애매하면 빼세요. 적을수록 좋습니다
- 시스템 알림은 Claude에게 CLAUDE.md가 "관련이 있을 수도, 없을 수도 있다"고 알려 줍니다. 잡음이 많을수록 더 무시됩니다
- 모노레포는 명확한 무엇/왜/어떻게 구조에서 가장 큰 효과를 봅니다
- 디렉터리별 CLAUDE.md 파일은 더욱 핵심에 집중해야 합니다
